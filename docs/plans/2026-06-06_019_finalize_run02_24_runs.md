## Changes
1. Finalize four trajectories:
   - cross `+/-30 mm`;
   - reverse grid 3x3 `+/-40 mm`;
   - diamond `+/-35 mm`, counterclockwise;
   - circle `r=40 mm`, counterclockwise.
2. Finalize the matrix as OFF/ON, three repetitions per trajectory:
   `4 x 2 x 3 = 24` runs.
3. Use a common `target_z=-263.27731514697575 mm`, waypoint hold `5 s`,
   circle `72` points over `30 s`, and `2 s` holds at the circle start/end
   point `(40, 0)`.
   - Record data on a deterministic `0.1 s` schedule.
   - Update serial commands at phase changes or every `0.5 s` to avoid
     backlog in the blocking Arduino smooth-move routine.
4. Use correction gain `0.25`, XY vector clamp `2 mm`, Z correction disabled,
   and the frozen Run 01 Ridge model.
5. Add a serial logger that:
   - builds the finalized trajectory and validates nominal IK;
   - records the existing Run 01-compatible main raw CSV;
   - requires a matching Simscape CSV for correction ON;
   - validates exact schedule/Simscape time-axis equality;
   - computes correction with the existing `CorrectionEngine`;
   - writes a separate auxiliary correction CSV;
   - falls back to nominal target/theta on inference or corrected-IK failure.
6. Add a 24-run manifest command that writes the exact run IDs and expected
   artifact paths without executing hardware.
7. Define run IDs as
   `YYYY-MM-DD_run02_<trajectory>_<off|on>_r01..r03`.
8. Define paired execution order by repetition and trajectory, OFF immediately
   followed by ON, to reduce configuration drift.

## Risk
- Correction ON cannot run without a Simscape CSV generated on the exact
  deterministic schedule.
- `theta*_meas` remains command echo and is not independent encoder feedback.
- PC/serial timing jitter remains possible even though scheduled timestamps are
  deterministic.
- Circle alignment still requires vision-side start/end holds and common event
  handling during post-processing.
